# shh.

Анонимный чат в реальном времени со **сквозным шифрованием (E2EE)**. Только переписка, ничего лишнего.

- **Ничего не сохраняется.** Ни базы данных, ни логов, ни `localStorage`/cookies. Всё живёт только в оперативной памяти браузера и сервера. IP-адреса не пишутся.
- **Сервер видит только шифртекст.** Он умеет лишь пересылать базовые blob'ы между клиентами. Ключи и открытый текст на сервер не попадают никогда.
- **Черно-белый минимализм, только тёмная тема.** Быстрая загрузка, нет внешних шрифтов, трекеров и CDN.
- **Криптография — на клиенте**, на нативном `Web Crypto API` (без сторонних библиотек).

## Структура проекта

```
Shh V1.0/
├─ package.json          # скрипты и зависимости (только ws)
├─ .gitignore            # node_modules, .env, логи и т.д.
├─ README.md
├─ server/               # Node.js (без фреймворка)
│  ├─ index.js           # HTTP + раздача статики + заголовки безопасности + CSP + upgrade на WS
│  └─ ws.js              # вся серверная логика: сессии в RAM, PoW, rate-limit, ретрансляция шифртекста
└─ public/              # фронтенд — чистый JS, без сборки
   ├─ index.html         # стартовый экран + двухпанельный интерфейс
   ├─ style.css          # тёмная тема, монохром, микро-анимации (120–200 мс)
   ├─ crypto.js          # X25519/ECDH + HKDF + AES-256-GCM + fingerprint + PoW
   ├─ media.js           # очистка метаданных (JPEG/PNG/WebP) и сжатие через canvas
   ├─ files.js           # нарезка файла на чанки по 64 КБ, сборка на приёме
   ├─ qr.js              # генератор QR-кодов (свой, без зависимостей)
   ├─ scan.js            # сканер QR: getUserMedia + BarcodeDetector / jsQR
   ├─ app.js             # протокол WebSocket, состояние сессии, UI
   └─ vendor/jsQR.js     # единственная сторонняя JS-зависимость (MIT, грузится лениво)
```

Единственная runtime-зависимость сервера — пакет [`ws`](https://www.npmjs.com/package/ws). Фронтенд не использует сборщика; в `public/vendor/` лежит только `jsQR` (MIT) — он подгружается **только** при открытии сканера и **только** в браузерах без нативного `BarcodeDetector` (Firefox, Safari).

## Запуск локально

Нужен Node.js 18+.

```bash
npm install      # ставит только ws
npm start        # поднимет сервер на http://localhost:3000
```

Откройте `http://localhost:3000` в двух разных браузерах/вкладках — это будут два собеседника.

Для разработки с автоперезапуском:

```bash
npm run dev
```

> Криптография `Web Crypto` требует защищённого контекста. `http://localhost` браузер считает защищённым, поэтому локально всё работает. В продакшене обязателен HTTPS/WSS (Railway даёт его из коробки).

## Деплой на Railway

Проект уже подготовлен:

- **Порт** берётся из окружения: `const PORT = Number(process.env.PORT) || 3000;` (`server/index.js`).
- **Скрипт запуска** — `npm start` → `node server/index.js` (Railway использует `start` из `package.json`).
- **WebSocket-адрес** клиент вычисляет сам через `location.host`, поэтому он автоматически совпадает с доменом Railway (`wss://<ваш-домен>` при HTTPS):

  ```js
  // public/app.js
  const WS_URL = () => `${location.protocol === 'https:' ? 'wss' : 'ws'}://${location.host}`;
  ```

- **`.gitignore`** исключает `node_modules/`, `.env` и логи.

Шаги:

1. Запушьте репозиторий в GitHub.
2. В Railway создайте проект из репозитория (New Project → Deploy from GitHub repo).
3. Railway сам определит Node.js, выполнит `npm install` и `npm start` и выдаст публичный HTTPS-URL (term-сервис). TLS-терминация включена автоматически → клиент подключится по `wss://`.
4. При необходимости выставьте переменную окружения `PORT` (по умолчанию Railway сам задаёт `PORT`, и приложение её читает).

Никаких дополнительных сервисов (БД, кэш) не требуется — всё в памяти процесса.

## Как пользоваться

1. **Создать сессию** — на стартовом экране одна кнопка. Перед созданием сервер выдаёт **PoW-задачу** (Proof-of-Work капчу): браузер должен подобрать nonce, чтобы `SHA-256(challenge:nonce)` начинался с нужного числа нулей. Это защита от ботов без внешних сервисов вроде Turnstile.
2. **Профиль** (круглая кнопка слева сверху) — показывает ваш идентификатор, публичный ключ и **QR-код идентификатора**. По умолчанию всё скрыто; одна кнопка «показать» открывает всё сразу, вторая — прячет и очищает canvas. В QR попадает **только идентификатор**, никогда — ключи. Кнопка **«Выйти»** завершает сессию сразу (без grace-периода) и создаёт новую: новые ключи, пустой экран, всё стёрто.
3. **Поиск** по 12-символьному идентификатору собеседника → **«Запрос»** на диалог. Рядом кнопка **«Сканировать QR»**: камера включается только по нажатию, после считывания ID подставляется в поиск, а запрос на диалог отправляется **только** по кнопке «Отправить запрос». Поток камеры останавливается при первом считывании, при «Закрыть» и по `Escape`.
4. Получатель видит карточку запроса и может **Принять** или **Отклонить**. Уведомление исчезает после принятия/отказа, а также после завершения чата — сервер рассылает событие обеим сторонам.
5. В чате справа сверху **«⋯» → «Завершить чат»**: чат мгновенно и полностью удаляется у обеих сторон (клиент и сервер) — история, ключи, вложения, открытое окно.
6. **Если собеседник вышел**, чат остаётся **только для чтения**: плашка «Собеседник отключился» (если он вернётся в течение grace-периода — плашка исчезает и ввод снова работает) или «Собеседник вышел» (окончательно). Поле ввода и кнопки заблокированы на клиенте, и сервер тоже отклоняет такие сообщения. Удалить чат можно кнопкой **«Удалить чат»**.
7. **Вложения**: кнопка скрепки в поле ввода. Файл до 5 МБ, метаданные вычищаются на клиенте, дальше файл шифруется тем же ключом чата и уходит чанками по 64 КБ с уникальным nonce на каждый. Превью и прогресс — в пузыре сообщения. Сервер не видит ни содержимого, ни имени файла, ни типа.
8. **Отпечаток ключа (fingerprint)** виден в шапке чата и в меню «⋯». Собеседники сверяют его по отдельному защищённому каналу — если коды совпадают, посредника (MITM) нет.

Сессия живёт, пока открыта вкладка. При закрытии вкладки/обрыве WS сервер сначала уведомляет собеседников (`peer_left`), ждёт короткий grace-период на перезагрузку страницы, а затем удаляет сессию, её чаты и связи (`peer_gone`). Сообщения **не хранятся**: если получатель офлайн, доставка не происходит (очередей нет, в том числе для файлов).

## Криптосхема (кратко)

Всё выполняется в браузере, на `crypto.subtle`.

| Шаг | Технология |
|-----|------------|
| Идентификация сессии | эфемерная пара **X25519** на сессию, приватный ключ не покидает браузер |
| Идентификатор | случайные 12 символов **base32** из CSPRNG (`crypto.getRandomValues`) |
| Общий секрет | **ECDH** на эфемерных ключах (свежая пара на каждый чат → forward secrecy) |
| Вывод ключа | **HKDF-SHA256** (salt = конкатенация отсортированных эфемерных публичных ключей, info = `shh-chat-v1`) → **AES-256** |
| Шифрование сообщений | **AES-256-GCM** с уникальным 96-битным nonce на каждое сообщение (`iv ‖ ciphertext ‖ tag`) |
| Вложения | тот же ключ чата, **AES-256-GCM** на каждый чанк по 64 КБ, свой nonce на чанк; метаданные файла вычищаются до шифрования |
| Отпечаток (MITM-проверка) | `SHA-256` от.identity+ephemeral публичных ключей обеих сторон, показывается как 4 группы hex |
| Защита от ботов | **PoW** на `SHA-256` (подбор nonce) перед созданием сессии |

### Установление ключа чата

1. Инициатор создаёт **эфемерную** пару `EphA` и вместе с запросом на диалог отправляет `EphA_pub` и `IdentityA_pub`.
2. Принятие запроса: респондер создаёт свою **эфемерную** пару `EphB` и отправляет `EphB_pub`.
3. Обе стороны считают общий секрет: `ECDH(EphA_priv, EphB_pub) == ECDH(EphB_priv, EphA_pub)` и через **HKDF** выводят один и тот же AES-256-GCM ключ.
4. Все сообщения шифруются этим ключом с **уникальным nonce**. Приватные эфемерные ключи хранятся только в памяти вкладки.

Так как на каждый чат создаются новые эфемерные ключи, компрометация одной сессии не вскрывает другие (**forward secrecy** на уровне чата). Сервер при этом пересылает только базовые blob'ы шифртекста и не имеет ни ключей, ни открытого текста.

### Совместимость кривой

X25519 в `Web Crypto` поддерживается современными Chrome/Edge/Firefox/Safari. Если движок не поддерживает X25519, клиент прозрачно откатывается на **P-256 ECDH** — кривая определяется по длине публичного ключа (32 байта = X25519, 65 байт = P-256), поэтому обе стороны автоматически договариваются об одной кривой. HKDF и AES-256-GCM остаются неизменными.

## Безопасность и ограничения

- **Размер текстового сообщения ≤ 2 КБ** — проверяется и на клиенте (`crypto.js: overSize`), и на сервере (`ws.js: validCipher`).
- **Файлы ≤ 5 МБ**, чанк ≤ 64 КБ открытого текста, не более 200 чанков на передачу. Сервер помнит только метаданные передачи (`transferId`, счётчик, срок), но не байты; при переполнении буфера получателя (`bufferedAmount`) передача прерывается, а не копится в памяти. Отдельные токен-бакеты на `file_open`, `file_chunk` и байты.
- **Rate limiting** на поиск, запросы на диалог, сообщения и файлы (токен-бакеты на соединение) — защита от перебора идентификаторов и спама.
- **Доставка только в живой чат.** Без adjacency (чат завершён или собеседник вышел) сервер отвечает `undeliverable`; очередей и store-and-forward нет.
- **Метаданные файлов удаляются на клиенте до шифрования**: имя и дата не передаются вовсе, MIME получатель определяет по содержимому. Из JPEG вырезаются EXIF/GPS/IPTC/XMP и комментарии, из PNG — `tEXt/iTXt/zTXt/eXIf/tIME/sCAL`, из WebP — чанки `EXIF`/`XMP ` (с очисткой флагов в `VP8X` и длиной `RIFF`). Форматы, которые нельзя очистить надёжно (GIF, BMP, HEIC, документы), отправляются только после явного предупреждения.
- **Камера** — только `Permissions-Policy: camera=(self)`, только по нажатию, поток всегда останавливается; кадры не сохраняются и не отправляются.
- **Только HTTPS/WSS** в проде; строгая **CSP** (`default-src 'self'`, без внешних источников, `frame-ancestors 'none'` и т.д.) и набор security-заголовков (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy: no-referrer`, `Permissions-Policy`, HSTS) — в `server/index.js`.
- **Без логов и без БД.** Сервер не сохраняет IP, содержимое или метаданные сообщений на диск.
- **Без store-and-forward.** Офлайн-получателю не доставляется ни сообщение, ни файл.

## Протокол WebSocket (для справки)

Клиент → сервер: `pow_challenge`, `create_session`, `search`, `contact_request`, `contact_response`, `message`, `file_open`, `file_chunk`, `file_abort`, `end_chat`, `delete_chat`, `exit`, `ping`.
Сервер → клиент: `pow_challenge`, `session_created`, `search_result`, `contact_request(_sent|_failed)`, `contact_response`, `message`, `file_open`, `file_chunk`, `file_aborted`, `chat_ended`, `peer_left`, `peer_back`, `peer_gone`, `undeliverable`, `error`, `pong`.

`peer_left` — связь пропала (grace-период открыт), `peer_back` — вернулась, `peer_gone` — сессия удалена окончательно. `exit` явного выхода из сессии grace-период не использует.

Сервер оперирует только идентификаторами и шифртекстом; поля `publicKey`/`ephPub` он пересылает как есть и не интерпретирует, а `file_*` несут случайный `transferId`, размер и число чанков — ни имени файла, ни MIME, ни содержимого сервер не видит.
